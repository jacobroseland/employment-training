# Supabase local development and migrations

## Local-first workflow

Supabase CLI runs a local Postgres database and the related Supabase services through a Docker-compatible runtime. In this project, OrbStack provides that runtime on macOS.

    npm install --save-dev supabase
    npx supabase init
    npx supabase start

`supabase/config.toml` is committed. It describes the reproducible local environment; Docker images, local database data, CLI caches, and secrets are not committed.

The local Studio dashboard is available at `http://127.0.0.1:54323`. Stop services when they are not needed:

    npx supabase stop

## Migrations are the schema history

Each intentional database change lives in an ordered SQL file under `supabase/migrations/`. The first migration creates `public.job_applications`, which mirrors the Job Search Pipeline model while using database-friendly names and types:

- `uuid` primary key generated by Postgres
- `date` for date-only application and follow-up fields
- `timestamptz` for creation and update times
- `text` plus `check` constraints for the current status and work-arrangement values
- nullable columns for optional form fields

Apply every migration from a clean local state and verify the schema has no drift:

    npx supabase db reset
    npx supabase db diff

`db reset` clears the local database, so use it for development/test data only. The migration files—not the local database volume—are the durable source of truth.

## Per-user browser access

The `job_applications` table enables Row Level Security from its first migration. A second migration adds a required `user_id` that references `auth.users`, grants CRUD privileges only to the `authenticated` database role, and defines four ownership policies.

Each policy compares `auth.uid()` with `user_id`, so a signed-in user can create, read, update, and delete only their own applications. The `anon` role has no access. Keep RLS policies and role grants together in the same migration: grants decide whether a role can reach a table, while RLS decides which rows it may use.

## Browser client configuration

Install the browser client with:

    npm install @supabase/supabase-js

Copy `.env.example` to `.env.local` and set only the browser-safe project URL and publishable key:

    VITE_SUPABASE_URL=https://<project-ref>.supabase.co
    VITE_SUPABASE_PUBLISHABLE_KEY=<publishable-key>

Never put a database password or a `service_role` key in a Vite environment variable. Values beginning with `VITE_` are included in the browser bundle. The repository ignores `.env.local` while committing `.env.example` as the documented template.

## App-wide authentication boundary

`AuthProvider` wraps the router in `src/main.tsx`. It owns the Supabase session lookup and subscription once, then provides the current user, loading state, configuration state, and sign-out action through React context.

Feature pages should own only feature data. For example, Job Search Pipeline reads the signed-in user from the auth context to load that user's applications; it does not render its own login form or subscribe to Supabase Auth. The reusable `AuthenticationPanel` lives in `src/components/` because the Account page, not a specific exercise, owns sign-in and account creation.

The exercise catalog marks each available exercise as either `public` or `account-required`. `ExercisePage` redirects an unauthenticated visitor from an account-required route to `/account?returnTo=...`, preserving the intended destination after sign-in. This is route-level UX protection; database RLS remains the actual data-security boundary.

The catalog groups installed account-required tools under **My personal apps** and public or uninstalled tools under **Explore apps**. Installation state is persisted separately from the static exercise catalog.

## User-installed apps

`user_app_installations` is a small join table with a composite primary key of `user_id` and `app_id`. It records a user's workspace choice without duplicating the static catalog metadata held in the frontend.

The catalog still decides which app IDs exist and whether they are public or account-required. The installation repository only reads, inserts, and deletes the signed-in user's rows. Its RLS policies mirror the job-application ownership model, so users can manage only their own app list. Installing an app is not a security permission; protected routes and the feature table's own RLS policies remain responsible for access control and data privacy.

## Local versus hosted

The local stack is for safe development and tests. The hosted project receives the same committed migrations with `npx supabase db push --remote`. Local and hosted environments use different URLs and keys through environment variables; never commit either environment's secret/service-role key.
